## Evidence vocabulary

| Term | Meaning | Permitted consumer |
| --- | --- | --- |
| **ACTIVE** | A specific persisted unresolved session, valid journal, live tab or admitted in-flight task is positively observed | Existing observer; blocks reservation |
| **UNKNOWN** | Missing/invalid/stale/read-failed or ambiguously terminal data; current/old worker or live account not independently proven | Existing observer; blocks reservation |
| **Source candidate** | A real storage key/controller/Chrome API that may supply evidence once validated, without a trusted `confirmed` signature | Wave A ledger only |
| **Independently proven IDLE** | All applicable starts and side effects are closed, cross-worker durable receipts reconciled, same live account/current generation bound, sources read-only and consistent **within one fenced snapshot** | **Not implemented; proposed Wave B/C contract** |
| **Remote outcome** | Independently verified same-account full My Ads/Ad-ID presence/absence result for a publish or source deletion, with intent/resolution identity match | P6 immutable journals; never inferred from UI redirect or local terminal status |

**Global invariant:** A provider must report confirmed IDLE only if every named source has an actual *positive absence* proof, not merely absence of observed ACTIVE entries. Missing status, stale session, caught storage error, terminal label, successful call, a closed tab or a previously matching profile is **UNKNOWN**, never IDLE.

## Cross-worker and external-effect closure required of *every* owner

1. **Admission continuity:** A single same-extension-origin exclusive Web Lock controls the start/reserve arbitration; all relevant autonomous, routed, late microtasks, tab events and callbacks must be fenced. A durable begin receipt written before the side effect and a validated immutable finish receipt must survive MV3 termination.
2. **Source completion:** Read real local/session/IndexedDB records with explicit schema validation and error propagation. Detect staged, queued, active, suspended, expired, missing and partially written work; an absent record is not a confirmed no-operation witness unless the producer contract proves absence under the lock.
3. **Remote outcome:** Account-bound publish/delete operations require independent fresh same-profile/Ad-ID verification; unresolved, corrupted or unverified P6 intent and Phase-4 outcome receipts block. **No** silently expired or automatically cleared uncertainty entries.
4. **Current live account:** A stored `activeDetectedProfileV1`/`selectedInventoryProfileV1` match is only a hint. An actual live website identity witness must be tied to the current request and reevaluated across snapshot/reserve/host handoff. A username/profile name alone is not assured to be a stable account identity.
5. **Worker generation:** `ownerWorkerInstanceId` is an in-process unique referent; `runtimeEpochV1` is a bulk-session epoch, **not** a worker generation. Any old-worker, stale callback or unaccounted background/document context blocks until a valid intergenerational completion proof exists.
6. **Atomic readback:** Verify all 15 independent sources and the lease record consistently under the same admission boundary; compare account, worker and data revision both before/after. Any mismatch, Web Locks failure, storage failure, concurrent start or nonce mismatch denies reserve.
7. **Host separation:** Even a correctly produced policy `candidate-idle` is **not** consent, host authentication, source-folder validation, Chrome-process-closed proof, staged/apply completion, or extension activation. Keep all independent updater gates.

## Blockers and decision for P1.3-B

- **Blocking by current design (15/15):** No code path can honestly emit the authoritative 15-owner positive-IDLE records. Neither observer supports a verified `idle` result; `getOwnerSnapshot` is absent from production. This is intentional fail-closed behavior and must not be weakened to satisfy an all-green fixture.
- **Missing operation-level crash evidence:** At least `singleInventory`, `trashMutation`, `diagnosticExport` and reset-owned work have no independent durable operation completion witness spanning app/MV3-worker termination. Many remaining owners have partial persisted sessions but no full proof that past detached tasks ended. This makes a positive lease **not currently derivable** from those sources alone.
- **Missing separate live-account witness:** `accountTransition` and `profileTransition` cannot be promoted from matching stored profile hints; current live probe has side effects. A trusted nonmutating, generation-bound observation mechanism must be specified and tested before wiring a provider.
- **Missing independent NativeHost state:** `nativeUpdateTransaction` cannot positively attest that a mutating host operation is absent, since no such host handshake or apply channel exists in production; this alone blocks fully authorized update activation.

**Wave A acceptance decision: inventory complete, implementation prerequisite open.** All 15 candidate sources, their consumers, async lifetimes, read/absence hazards and proposed independent positive IDLE criteria are documented. The actual ability to emit trustworthy positive owner records is **blocked**, which is the precise handoff to P1.3-B design/test RED. This document must not be used to check P1.3 itself, P9's first prerequisite, or authorize an update/release.

**No runtime mutation / live-account operation:** This file is documentation only. `main` (v1.23.49), the Work v1.23.51 ZIP, extension ID, native permissions, scripts, tests and runtime source remain unchanged by this Wave.


## P1.3-E3C identity requirement clarification (owner decision 2026-11-10)

The actual Kleinanzeigen Manager already enforces live logged-in site account to selected inventory-profile matching through its existing `PAGE_STATUS.profileName` / `detectedProfileName`, `AccountProbeService`, `AccountSessionController.assertSelectedProfileMatchesLiveAccount`, and application `AccountGate`. The owner explicitly selected **reuse of this existing match**: do not introduce a second vendor seller-id lookup or validate email address syntax. Kleinanzeigen handles its own account authentication; the manager compares the identity label made available to its existing gate.

The additional owner observer now classifies only a *consistent* read-only, twice-read, logged-in `PAGE_STATUS.profileName` matching a stable selected/local profile as `context.profile.state='matched'`. Site logout, two differing tab identities, profile changes, missing scripts or a changed second site status remain `unverified`. This matching assertion does **not** prove IDLE for any of the 15 owners, a cross-worker-complete remote operation, or native transaction recovery. The observer's `eligibleForLease` remains `false` and the production updater-fence lacks a trusted all-owner provider; no positive reserve is authorized. Other relevant P1.3-C/D, P9 and P10 acceptance conditions remain.


## P1.3-E3D — private source wiring for existing site identity (2026-11-10)

The private `KRTrustedOwnerAuthority` now accepts the **existing** read-only `KRAdditionalOwnerObserver.observe()` source contract, not a synthetic `accountId`. It requires `schema:1`, `eligibleForLease:false`, a current matching `context.profile` with `LIVE_ACCOUNT_PROFILE_MATCH`, current worker instance binding and a fresh observation. The producer itself checks the authenticated `PAGE_STATUS.profileName` twice, matched against the already selected local inventory profile with read-back. The production background injects only `readLiveAccountReadOnly: () => requireAdditionalOwnerObserver().observe()` into the private authority; it does **not** provide the missing per-owner source completion producer, tab attestation or any app/message route.

The test-only positive owner proofs must **never** be confused with this production wiring: `KRTrustedOwnerAuthority.captureForReserve` and `reserveThroughFence` remain fail-closed without the other required private producers. A match grants **no** update privilege. All 15 genuine owner completion receipts, cross-generation proof, NativeHost transaction verification, Phase P9 full safety prerequisite and Issue #99 remain OPEN. No permission or website functionality change.


## P1.3-F1 — independently corroborated live managed-tab absence source (2026-11-10)

The P1.3-F1 source step adds the readVerifiedUnmanagedTabsReadOnly() method to the existing KRAdditionalOwnerObserver for the private KRTrustedOwnerAuthority browser-tab reader. Under the existing admission Web Lock it reads raw tabRegistryV1 and managedWorkerTabsV1 from Chrome session storage, enumerates Chrome tabs, then independently reads both again. Any read failure, missing/malformed registry, changed result, duplicate/unregistered tab, active managed tab, contradictory GONE tombstone, unresolved legacy tab, inconsistent source/role or partial closing intent denies classification. No migrations, tab creation, navigation, recovery or storage writes occur. A positive result certifies only the currently enumerated individual unmanaged tabs, NOT the entire managedTabs owner or any prior worker's completion and NOT all-15 IDLE. No updater lease, NativeHost operation, public route or privileged permissions are granted. Original P1.3 and P9 safety closure remain open.
